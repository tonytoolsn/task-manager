# 一人團隊操作手冊

> 個人任務管理系統 · Laravel API + React
> 建立日期:2026-08-20

---

## 這份文件怎麼用

每次坐下來工作前,先問自己一句:**我現在戴哪頂帽子?**

翻到那一節,照著做。做完之後,在 `learning-log.md` 記一筆。

不要同時戴兩頂帽子。這是整份文件唯一一條不能破的規則。

---

## 五頂帽子總覽

| 帽子 | 你在扮演 | 主要產出 | 什麼時候戴 |
|---|---|---|---|
| 🎩 PM | 產品經理 | Backlog、驗收條件 | Sprint 開始與結束 |
| 🎨 設計 | UI/UX 設計師 | 線框稿、元件規範 | 開票之後、開發之前 |
| ⚙️ 後端 | 後端工程師 | API + 測試 + 文件 | Sprint 前半 |
| 💻 前端 | 前端工程師 | 元件 + 串接 | Sprint 後半 |
| 🚀 DevOps | 維運工程師 | CI/CD、部署、監控 | Sprint 結束前 |

## 🎩 帽子一:PM(產品經理)

### 職能定義
決定「做什麼」和「不做什麼」。你是唯一有權力改變範圍的人。

### 核心技能

| 技能 | 具體是什麼 | 怎麼練 |
|---|---|---|
| 需求拆解 | 把「我要任務管理」拆成 20 張可執行的票 | 每張票問:一天做得完嗎? |
| 驗收條件撰寫 | 用可勾選的句子定義「完成」 | 寫成「使用者可以…」或「當…則…」 |
| 優先級判斷 | 決定 P0/P1/P2 | 問:沒有它,系統還能用嗎? |
| 範圍控制 | 拒絕自己的新點子 | 一律丟 Backlog,不進本期 |

### 產出文件

```
docs/
├── PRD.md              產品需求文件(一頁)
├── backlog.md          需求池(或直接用 GitHub Issues)
└── sprint-01.md        本期 Sprint 目標與票單
```

### 一張好票的格式

```markdown
## 需求
（一句話說明使用者要什麼)

## 驗收條件
- [ ] 具體、可驗證的條件
- [ ] 錯誤情況也要寫
- [ ] 有對應的測試

## 相關
API 規格 §3.1、線框稿 2c

## 估時
0.5 天
```

### 紀律

- **Sprint 開始後不改範圍。** 想到新東西 → 開 Issue、標 `P1`、丟 Backlog、關掉念頭。
- **驗收時不放水。** 驗收條件沒全過就是沒完成,不能自己說「差不多了」。
- **估時要記錄實際花費。** 三個 Sprint 之後你才會估得準。

### 常見失敗
> 「這個順便一起做好了」——這句話出現時,你已經破功了。

## 🎨 帽子二:設計

### 職能定義
決定「長什麼樣」和「怎麼操作」。你要在寫程式之前,把畫面上的每個元素都想清楚。

### 核心技能

| 技能 | 具體是什麼 | 怎麼練 |
|---|---|---|
| 線框稿 | 灰階版面結構圖 | 每頁 15~30 分鐘,不上色 |
| 資訊層級 | 決定使用者第一眼看到什麼 | 瞇眼看畫面,最顯眼的是最重要的嗎? |
| 狀態設計 | 空狀態、載入中、錯誤、成功 | 每個畫面都要問這四個狀態長怎樣 |
| 元件思維 | 找出重複出現的元素 | 同樣的東西出現兩次 → 抽成元件 |

### 產出文件

```
docs/
├── wireframes/         線框稿圖片
│   ├── 01-task-list.png
│   ├── 02-task-form.png
│   └── 03-empty-state.png
└── ui-notes.md         元件規範、狀態說明
```

### 每個畫面必問的四個狀態

| 狀態 | 問題 |
|---|---|
| 空狀態 | 一筆資料都沒有時,顯示什麼? |
| 載入中 | 資料還沒回來時,畫面是什麼? |
| 錯誤 | API 掛掉時,使用者看到什麼? |
| 成功 | 操作成功後,有什麼回饋? |

**新手最常忘記的是「載入中」和「錯誤」。** 這兩個沒設計,你的前端就會在網路慢的時候變成一片空白。

### 紀律

- **開發中發現設計有問題 → 回頭改線框稿,不是直接在程式裡改。** 不然文件和實作會分家。
- **第一版不做視覺美化。** 顏色、字體、動畫全部延後到系統能跑之後。
- **線框稿只畫本期要做的。** 不要預先畫 P1、P2,那些會白畫。

## ⚙️ 帽子三:後端工程師

### 職能定義
把資料存好、把 API 開好、確保沒有安全漏洞。

### 核心技能

| 技能 | 具體是什麼 | 對應到 Laravel |
|---|---|---|
| 資料建模 | 設計資料表與關聯 | Migration、Eloquent Model |
| API 設計 | RESTful 路由、狀態碼 | `routes/api.php`、Resource |
| 輸入驗證 | 不信任前端送來的任何東西 | FormRequest |
| 授權控制 | 確保使用者只能存取自己的資料 | Policy、`$user->tasks()` |
| 測試 | 每支 API 至少兩個測試 | Pest / PHPUnit Feature Test |
| 資料庫效能 | 避免 N+1 查詢 | `with()` eager loading |

### 產出文件

```
docs/
├── api-spec.md         API 規格(端點、參數、回應、錯誤碼)
├── erd.md              資料模型說明
└── adr/                技術決策紀錄
    ├── 001-why-laravel.md
    └── 002-date-vs-datetime.md
```

### 寫一支 API 的標準流程

```
1. 看票的驗收條件
2. 先寫測試（測試會失敗,這是正常的)
3. 寫 Migration / Model（如果需要)
4. 寫 FormRequest 驗證
5. 寫 Controller
6. 跑測試,直到綠燈
7. 更新 api-spec.md      ← 最常忘記的一步
8. 開 PR
```

### 每支 API 的自我檢查清單

- [ ] 有沒有驗證輸入?
- [ ] 有沒有確認使用者只能碰自己的資料?
- [ ] 錯誤情況回傳正確的狀態碼嗎?
- [ ] 有沒有 N+1 查詢?(用 `with()` 了嗎)
- [ ] 測試涵蓋正常和錯誤各一個嗎?
- [ ] api-spec.md 更新了嗎?

### 紀律

- **改了 API 就要改文件。** 這是五頂帽子中最容易破功的地方,因為改文件沒有成就感。
- **先寫測試再寫程式。** 不是為了純粹,是為了逼你先想清楚「這支 API 到底該回什麼」。
- **不要為了前端方便而破壞 API 設計。** 前端有前端的解法。

## 💻 帽子四:前端工程師

### 職能定義
把 API 的資料變成使用者看得懂、點得動的畫面。

### 核心技能

| 技能 | 具體是什麼 | 對應到 React |
|---|---|---|
| 元件拆分 | 決定什麼該獨立成元件 | 重複出現 → 抽出來 |
| 狀態管理 | 資料放哪裡、誰能改 | useState、Context |
| 資料抓取 | 呼叫 API、處理載入與錯誤 | axios + 自訂 hook |
| 表單處理 | 輸入、驗證、送出 | 受控元件 |
| 響應式 | 手機和桌面用同一份程式碼 | Tailwind 的 `md:` 前綴 |

### 產出文件

```
docs/
└── component-map.md    元件樹狀圖與職責說明
```

### 串接 API 的標準流程

```
1. 打開 api-spec.md（不要去看後端程式碼)
2. 用 Postman / Thunder Client 手動打一次,確認回傳格式
3. 寫 API 呼叫函式
4. 處理三種狀態:loading / error / success
5. 接上畫面
6. 手機版檢查一次
```

### 每個元件的自我檢查清單

- [ ] 載入中的畫面做了嗎?
- [ ] API 失敗時顯示什麼?
- [ ] 空資料時顯示什麼?
- [ ] 手機版看起來正常嗎?
- [ ] 按鈕重複點擊會不會送出兩次?

### 紀律

- **只依照 API 文件寫,不准用「我知道後端怎麼寫的」作弊。**
  如果文件不夠你寫 → 那是文件有問題,回去戴後端帽子補文件。
  **這是整套模擬中最有價值的練習。**
- **不要在前端做後端該做的判斷。** 例如「完成時要設 completedAt」這種業務規則,一定在後端。

## 🚀 帽子五:DevOps

### 職能定義
讓程式碼從你的電腦,安全地跑到網路上。

### 核心技能

| 技能 | 具體是什麼 |
|---|---|
| 版本控制 | 分支策略、PR 流程、commit 規範 |
| CI | 自動跑測試,PR 沒過不能 merge |
| 環境管理 | 本機 / 測試 / 正式,設定分離 |
| 部署 | 前後端分別部署、環境變數、資料庫遷移 |
| 監控 | 出錯時你要知道 |

### 產出文件

```
docs/
├── deployment.md       部署步驟、環境變數清單
└── runbook.md          出事時怎麼辦
.github/
├── workflows/ci.yml    CI 設定
├── pull_request_template.md
└── ISSUE_TEMPLATE/
```

### Git 規範

**分支命名**
```
feat/12-task-filter        新功能
fix/23-timezone-bug        修 bug
refactor/31-extract-hook   重構
docs/8-update-api-spec     文件
```

**Commit 訊息(Conventional Commits)**
```
feat(task): add status filter to task list API
fix(task): correct overdue calculation for timezone
test(task): add cases for invalid status value
docs(api): update POST /api/tasks response example
refactor(ui): extract TaskCard component
chore(deps): bump laravel to 11.9
```

格式:`type(scope): 動詞開頭的英文描述`

### 紀律

- **main 分支設為 protected,永遠不直接 push。**
- **每個 Sprint 結束一定要部署一次**,不管功能完成度。
- **環境變數不進 Git。** `.env` 加進 `.gitignore`,另外維護 `.env.example`。

## 換帽子的規則

### 三條鐵則

**1. 一次只戴一頂**
寫後端時發現前端會很難處理 → 記在 daily log,不要當場切過去改。

**2. 換帽子要留下交接紀錄**
就像真的交接給另一個人。在 daily log 寫:
```
[後端 → 前端]
交接:GET /api/tasks 已完成,回應格式見 api-spec.md §3.1
注意:project 欄位可能是 null（任務未歸屬專案時)
```

**3. 不准用另一頂帽子的知識作弊**
這是最違反直覺、也最重要的一條。詳見前端帽子的紀律段落。

### 一週的帽子分配範例

| 日 | 帽子 | 內容 |
|---|---|---|
| 一 | 🎩 PM | Sprint Planning、開票 |
| 二~四 | ⚙️ 後端 | 寫 API + 測試 |
| 五 | 🎨 設計 | 補畫下一頁線框稿 |
| 六~日 | 💻 前端 | 串接畫面 |
| (期末) | 🚀 DevOps | 部署 + Review + Retro |

## 學習紀錄制度

這是你「模擬上班」和「真的在學東西」之間的橋樑。三個檔案就夠。

### 1. `daily.md` — 每天 3 分鐘

```markdown
## 2026-08-21 ⚙️ 後端

昨天:完成 #3 GET /api/tasks
今天:#4 POST /api/tasks
卡住:date 欄位存 date 還是 datetime,今天要決定

---
```

**「卡住」那行最重要。** 連續三天出現同一句 → 那不是卡住,那是你在逃避,該找人問或換方法。

### 2. `learning-log.md` — 每學到一個新東西就記

```markdown
## Eloquent 的 N+1 問題

**情境**
`GET /api/tasks` 回傳 20 筆任務,結果跑了 21 次 SQL 查詢。

**原因**
每筆任務取 `$task->project` 時,Eloquent 都額外查一次資料庫。

**解法**
```php
Task::with('project')->get();
```

**延伸**
Laravel Debugbar 可以看到每個請求的 SQL 次數。
可以用 `Model::preventLazyLoading()` 在開發環境直接報錯。

**踩到的日期**:2026-08-25 · 花了 40 分鐘
```

**格式重點:情境 → 原因 → 解法 → 延伸。**
只寫解法,三個月後你會看不懂為什麼要這樣做。

### 3. `retro.md` — 每個 Sprint 結束

```markdown
## Sprint 1（8/21 - 9/03)

**目標達成率**:8 張票完成 6 張

**做得好**
- 測試有寫,重構 TaskController 時完全不緊張

**做不好**
- API 文件又忘記更新,兩次
- #7 estimated 0.5 天,實際花 2 天(低估了時區處理)

**下次改**
- PR 模板加一個 checkbox:「api-spec.md 已更新?」
- 估時遇到「時間/日期」相關的票,一律乘 2

**學到最有價值的一件事**
先寫測試不是為了品質,是為了逼自己先想清楚 API 該回什麼。
```

### 怎麼避免這件事變成負擔

- daily 三行就好,不要寫成日記
- learning-log 只記「卡超過 15 分鐘」的東西,小事不記
- retro 十分鐘,不要開檢討大會

**抓 70% 就好。** 目標是養成肌肉記憶,不是產出完美文件。

## 三個月後的驗收標準

不是「功能做完了幾個」,而是:

- [ ] 有一個網址,別人打開就能用
- [ ] `learning-log.md` 有 20 則以上
- [ ] 能對著 `api-spec.md` 跟別人解釋你的系統怎麼運作
- [ ] 有一次「因為有測試,所以敢大改」的經驗
- [ ] 有一次踩到坑、寫進 retro、下個 Sprint 沒再犯的經驗

**最後兩項是真正把新手和有經驗的人分開的東西。**
